# wb-mqtt-dmx — план v0.1

> Статус: прототип для проверки UX/UI и теорий на железе. Код намеренно простой и плоский,
> без глубоких абстракций: после проверки его перепишет программист.

Дата: 2026-11-03. Драйвер DMX512 для контроллера Wiren Board: выдаёт DMX со штатного порта
RS-485 или модуля WBE2-I-RS485-ISO, приборы публикует как MQTT-устройства. Отдельный
репозиторий `C:\Users\levio\Repo\wb-mqtt-dmx`, remote подключается позже.

## 2. Архитектура

```
MQTT (/devices/dmx_*/controls/*/on)
        │
        ▼
 DmxService ── конфиг, шаблоны, устройства, группы, persistence
        │  пишет целевые байты
        ▼
 Universe[N] ── буфер 512 байт на вселенную (lock)
        │  snapshot() раз в период
        ▼
 FrameSender[N] ── поток на вселенную, сетка t0 + k·period, учёт опозданий
        │
        ▼
 SerialDmxOutput ── termios2 250000 8N2, BREAK/MAB через ioctl, DE через RTS
```

Модули пакета `wb/mqtt_dmx/`:

| Модуль | Ответственность |
|---|---|
| `output/serial.py` | открыть порт, 250000 8N2 (`TCSETS2` + `BOTHER`), выключить авто-RS485 (`TIOCSRS485`), держать DE через RTS (`TIOCMBIS`), кадр = `TIOCSBRK` → ≥88 мкс → `TIOCCBRK` → ≥8 мкс → `write(0x00 + слоты)`, перед следующим кадром ждать `TIOCOUTQ==0` и `TEMT`; при закрытии вернуть rs485-настройки |
| `sender.py` | поток кадров, настраиваемая частота 1…44 Гц, статистика fps/late, переоткрытие порта по ошибке раз в 5 с |
| `universe.py` | буфер вселенной, запись блоками, снимок для отправки |
| `templates.py` | загрузка шаблонов декодеров из `/usr/share/wb-mqtt-dmx/templates` и `/etc/wb-mqtt-dmx.conf.d/templates`, валидация |
| `config.py` | разбор `/etc/wb-mqtt-dmx.conf`: вселенные, приборы, `count`, автоадрес, проверка пересечений |
| `service.py` | MQTT-устройства по конвенциям WB, обработка записей, группы, blackout, статус |
| `state.py` | сохранение значений каналов в `/var/lib/wb-mqtt-dmx/<universe>.json` (не чаще раза в секунду), восстановление при старте |
| `main.py` | CLI: запуск сервиса, `test-port`, `update-schema`, `templates` (список) |

Порт у каждой вселенной свой; одна вселенная = один поток; MQTT-колбэки только меняют буфер.

## 3. Конфигурация

`/etc/wb-mqtt-dmx.conf` (форма confed генерируется из схемы, список типов — из шаблонов):

```json
{
  "universes": [
    {
      "id": 1, "name": "Фасад",
      "port": "/dev/ttyRS485-2",
      "refresh_hz": 40, "slots": 512,
      "break_us": 176, "mab_us": 20,
      "on_start": "restore",            // restore | zero | scene
      "start_scene": {"1": 255, "2": 0}, // для on_start = scene, канал -> значение
      "on_stop": "hold",                // hold | blackout
      "raw_channels": 0                 // >0 -> устройство dmx_u1 с ch1..chN
    }
  ],
  "devices": [
    {"id": "bridge", "name": "Пролёт", "type": "rgbw", "universe": 1, "address": 1, "count": 40},
    {"id": "sign",   "name": "Вывеска", "type": "dimmer", "universe": 1, "address": 0},
    {"id": "fog",    "name": "Дымомашина", "type": "raw-8", "universe": 1, "address": 300}
  ]
}
```

Шаблон декодера `/usr/share/wb-mqtt-dmx/templates/rgbw.json`:

```json
{
  "type": "rgbw",
  "title": {"en": "RGBW decoder", "ru": "Декодер RGBW"},
  "channels": [
    {"id": "red",   "title": {"en": "Red",   "ru": "Красный"}, "default": 0},
    {"id": "green", "title": {"en": "Green", "ru": "Зелёный"}, "default": 0},
    {"id": "blue",  "title": {"en": "Blue",  "ru": "Синий"},   "default": 0},
    {"id": "white", "title": {"en": "White", "ru": "Белый"},   "default": 0}
  ]
}
```

Базовый набор: `dimmer`, `rgb`, `grb`, `rgbw`, `grbw`, `drgb` (общий диммер первым), `drgbw`, `cct`
(тёплый/холодный), `rgbcct`, `raw-N` (N каналов `ch1…chN`, N из конфига). Порядок каналов — порядок в
массиве, занимаемые адреса — длина массива. Поле `channel` в шаблоне позволяет пропуски (`"channel": 6`).

## 4. MQTT-модель

| Устройство | Контролы |
|---|---|
| `wb-mqtt-dmx` (служебное) | `status` text; на вселенную `universe_N` text («/dev/ttyRS485-2: 40.0 fps, 12345 кадров, 0 late» или «error: …»); `devices` value; `addresses` text (карта адресов); `blackout` pushbutton |
| `dmx_<id>` (прибор) | по каналу шаблона: `range` 0–255 с заголовками en/ru; `profile` text («RGBW · U1 DMX 1–4»); `meta/error` = `w` пока порт не открыт |
| `dmx_<id>` (группа при `count`>1) | те же контролы; запись уходит во всех членов, показывает последнее записанное |
| `dmx_uN` (сырые, при `raw_channels`>0) | `ch1…chN` range 0–255 |

Все `meta` retained при старте, при остановке — очистка retained-топиков (как у wb-dmx-fixtures).
Значения контролов = целевые значения каналов, публикуются при записи и при восстановлении.

## 5. Проверка на железе

Команда без MQTT: `wb-mqtt-dmx test-port /dev/ttyRS485-2 --pattern blink --seconds 30` (`full`, `ramp`,
`blink`). Матрица:

| Платформа | Что проверить | Чем |
|---|---|---|
| WB8 (wb-2609) | 250000 через BOTHER принят, BREAK ≥ 88 мкс, MAB ≥ 8 мкс, DE держится весь кадр, 512 слотов × 40 Гц без пропусков 10 минут, нагрузка CPU | осциллограф на A/B, `top`, счётчик late |
| WB7 (armhf) | то же; отдельно — слушается ли DE RTS при выключенном rs485-режиме (драйвер sunxi) | осциллограф, декодер |
| WB6 | то же; CPU и память | `top` |
| WBE2-I-RS485-ISO (`/dev/ttyMODx`) | кто управляет направлением (RTS или автомат модуля), держит ли 250 кбод, `de_control: none` как запасной вариант | осциллограф |
| Любой + wb-mqtt-serial | порт включён в serial-конфиге → драйвер не открывает порт, статус с подсказкой; после отключения порта в UI — поднимается сам | UI, `fuser -v /dev/ttyRS485-2` |

Известные ограничения по чужому опыту (DMXWB, C++ на WB8): 300 слотов/44 Гц стабильно, 512/40 с
редкими опозданиями. Для Python ожидаем похожее или хуже — измерить, при необходимости по умолчанию
30 Гц и/или переписать `output/serial.py` на C-хелпер.

## 6. Пакет и поставка

- `wb-python-service-template`: `setup.py`, `debian/` (`control`, `rules`, `install`, `postinst`, юнит), `wbdev ndeb`.
- Зависимости: `python3-wb-common` (MQTT-клиент), стандартная библиотека. Без pyserial.
- Юнит: `After=mosquitto.service`, `Restart=on-failure`, выход 6 = ошибка конфига (не перезапускать).
- Схема confed: генерируется из шаблонов (enum типов) в `/var/lib/wb-mqtt-confed/schemas/wb-mqtt-dmx.schema.json`.
- Тесты: pytest на host (ioctl подменяются фейком), линтеры по `wirenboard/codestyle` (black, isort, pylint).
- Документация: README (ru), `docs/dmx_serial_port.md` (как устроен выход, как отдать порт, что мерить).

## 8. Бэклог (после v0.1)

Решения по приборам и шаблонам (2026-11-04):
- Простые приборы описываются строкой раскладки как в Home Assistant (`dRGBW`, 8/16 бит), тип по умолчанию;
  «Каналы» для сырого доступа; сырого устройства на порт и палитры (контрола `rgb`) нет — только ползунки по каналам.
- Режим прибора (personality) в JSON-шаблонах = отдельный тип на режим («MH-X50 (14 ch)»); конвертер из
  OFL/GDTF будет генерировать по файлу на режим. Автоопределение режима по RDM — вместе с обнаружением.
- Каналы с диапазонами (строб, программы, колёса): в шаблоне `ranges` → контрол `value` с `enum` плюс
  0…100 % внутри непрерывного диапазона. Отложено, код маппинга есть в прототипе на MGU.
- Буквы раскладки `m` (режим) и `s` (строб), 2026-11-17: у дешёвых PAR канал после «режима» в ручном
  режиме задаёт строб, а в программах — скорость. Пока оставлено `s` «Строб»; логичнее назвать канал
  «Скорость» (отдельной буквой или переименованием).
- Выпадающий список режимов (2026-11-17, попробовали и откатили): у прибора в форме было текстовое поле
  «Режимы» (`0 Ручной, 51 Скачки, 101 Перелив`), с ним канал `m` публиковался как `value` с `enum`, и
  homeui 2.267 рисовал в карточке прибора выпадающий список (проверено). В DMX шла середина диапазона,
  любое записанное число относилось к своему диапазону. Откатили из-за формы: длинная строка в узкой
  ячейке таблицы выглядит плохо, а спрятать поле у приборов без `m` редактор не может — зависимости
  работают только по точному значению другого поля. Буква `m` осталась обычным ползунком 0–255.
  Код списка есть в истории ветки (коммиты 54223d8, d283782). Искать вариант изящнее: отдельный тип
  «Раскладка с режимами», готовые наборы режимов или диапазоны в шаблоне прибора.
- «Китайский DMX» (обзор форумов и документации ETC, ENTTEC, ChamSys, Avolites, 2026-11-17). Отдельного
  протокола нет, это приёмники, сделанные с отступлениями от DMX512. Что ломается и чем лечат:
  (1) не успевают за полным темпом — снижают частоту до 24–33 Гц, удлиняют BREAK и MAB, добавляют паузу
  между байтами (у ETC в режиме Slow: BREAK 264–320 мкс, MAB 84–100 мкс, пауза между байтами 36–46 мкс);
  (2) не проверяют стартовый код и дёргаются от пакетов RDM — RDM на порту выключают;
  (3) не любят «плавающие» тайминги сигнала, собранного программой на ПК;
  (4) путаются от коротких кадров, некоторым нужны все 512 каналов;
  (5) при пропаже сигнала уходят в автопрограмму — шлюзы умного дома, которые шлют только при изменении;
  (6) железо: перепутанные контакты 2 и 3, нет развязки, слабые блоки питания.
  У нас: поток непрерывный, RDM нет, BREAK, MAB, частота и число слотов настраиваются, по умолчанию
  40 Гц × 512. Проверено на двух дешёвых PAR: работают на настройках по умолчанию.
- Пауза между каналами (2026-11-17, сделано): настройка порта «Пауза между каналами, мкс» в разделе
  «Дополнительно», по умолчанию 0. UART сам паузу не делает, поэтому кадр пишется по одному байту со сном
  между ними; сон под SCHED_FIFO длиннее заказанного на 10–25 мкс, минимум вычитается. Период кадров сам
  подстраивается под реальную длину кадра. Проверено осциллографом (docs/hardware_results.md): задано
  50 мкс — медиана 53 мкс, 15–17 Гц при 512 каналах; задано 20 мкс — медиана 21 мкс, 23,5 Гц; соседний порт
  держит 40 Гц. Первый вариант с активным ожиданием держал блокировку интерпретатора и ронял соседний порт
  с 40 до 17 Гц. Не проверено: польза на приборе, которому пауза нужна.
- Библиотеки: OFL (656 приборов, без декодеров), GDTF (3000+ приборов, аккаунт), QLC+ — не встраивать,
  а конвертировать в наши шаблоны по ссылке/файлу.
- RDM (обнаружение, адрес и режим с контроллера, «мигнуть») — главный путь к настройке без рук; у декодеров
  для лент есть у Sunricher, у сценических приборов почти везде.

Сцены и вход из сети (2026-11-04):
- Стенд wb-dmx-demo-stand (сцены в wb-rules, кадр каждые 50 мс по MQTT в каналы) перенесён на наши
  устройства как эксперимент (в репозиторий не вошёл, стоит на тестовом контроллере): UX хороший, цена плохая — wb-rules ~40 % ядра на двух
  приборах, драйвер 2 → 10 %. Решение: кадры не рисовать снаружи. Порядок работ: (1) плавность перехода в
  драйвере (контрол «Плавность, с», интерполяция в потоке кадров), (2) сцены-снимки с кнопками и
  мастер-яркостью, (3) несколько встроенных динамических эффектов. wb-rules остаётся для логики
  «датчик → сцена».
- QLC+ и подобные пульты не умеют MQTT (только Art-Net/sACN/OSC/USB), ставить их на контроллер не нужно:
  сделан **вход Art-Net и sACN** (`netin.py`). Пульт главный, пока шлёт (LTP среди равных, выше приоритет
  sACN — выше), через 2,5 с тишины или по sACN stream-terminated порт возвращается к значениям MQTT.
  Контролы приборов следуют за пультом не чаще 4 раз в секунду, источник виден в `<port>_source`
  («Art-Net 192.168.13.195 · 40 fps»). По умолчанию выключено (раздел «Приём из сети» у порта), вселенные
  по умолчанию Art-Net 0,1,… / sACN 1,2,…; ArtPoll → ArtPollReply, так что QLC+ видит контроллер в
  списке нод. Измерено на WB8: полный кадр 512 каналов на 40 fps с изменением всех каналов — драйвер
  ~10 % ядра (из них большая часть — публикация ~45 контролов 4 раза в секунду), mosquitto ~6 %.
  Проверка: `scripts/net_send.py HOST --proto artnet|sacn --universe N`, `--poll` для ArtPoll.
  Слияние двух пультов вживую не проверено.
- Проверено с QLC+ 4.14.1 на самом контроллере (`qlcplus --nogui --web --operate`, веб на :9999, проект
  /root/qlcplus-demo/wb-demo.qxw, вывод Art-Net на 127.0.0.1): сцены и RGB-матрица доходят до приборов,
  драйвер ~5 % ядра, QLC+ ~2 %. Что выяснилось: «Universe 1» в QLC+ = адрес Art-Net 0 (наш второй порт
  по умолчанию слушает 1 — надо сводить руками); неизменную вселенную QLC+ шлёт раз в 2 с, поэтому таймаут
  Art-Net 5 с (sACN 2,5 с по E1.31); на одном хосте оба бьют 6454 с SO_REUSEADDR и unicast доходит до
  драйвера при любом порядке запуска; запущенный QLC+ держит порт даже без активной сцены (шлёт нули как
  keepalive), так что пока он работает, ползунки в homeui на линию не влияют.


- Переходы (transition у прибора и группы) и сцены — «типовая» надстройка, язык/место не решены.
- Семантические контролы поверх каналов: `color` rgb, `brightness`, цветовая температура (как у wb-led).
- Профили OFL (есть готовый код в `dmx_mgu/controller/wb-dmx-fixtures`).
- Другие выходы за тем же интерфейсом: шлюз WB-MGU по Modbus TCP, USB-FTDI (вход Art-Net/sACN сделан).
- Вход из сети: HTP-слияние как опция, выход OSC в пульт (запуск кью из wb-rules), ArtPollReply на
  несколько net/subnet (сейчас один ответ на все порты).
- RDM (адресация декодеров с контроллера), вход DMX.
- Интеграция: примеры wb-rules, страница вики, шаблон в wb-mqtt-serial не нужен (порт у нас).

## 9. Риски

| Риск | Что делаем |
|---|---|
| DE не слушается RTS на WB7/WBE2 | `de_control: none` (кернел сам), проверка на этапе 1 до написания MQTT-части |
| Джиттер Python на 512/40 Гц | по умолчанию 30 Гц или C-хелпер для цикла кадров |
| Второй писатель на порту | проверка serial-конфига + документация, как у mbgate |
| Тяжёлая карточка при `raw_channels` = 512 | по умолчанию 0; документировать |
| `rx_trig_bytes` и прочие sysfs-настройки wb-mqtt-serial остаются на порту | не мешают передаче; отметить в docs |
